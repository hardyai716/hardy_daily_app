## 页面 v5：iOS 视觉风格 + 长文本错乱修复

### 长文本错乱根因（前端通用问题）
- `.record-row{display:grid;grid-template-columns:42px 1fr auto 32px}` 里，文本列是 `1fr`，
  但 `.record-main`（grid 子项）没有 `min-width:0`，而 `1fr` 的最小值是 `auto`，
  于是超长商户名会把 `1fr` 轨道顶开，把金额列和删除按钮推出去 → 列不对齐。
- 解法三件套：① 文本列 `min-width:0`；② 标题 `-webkit-line-clamp:2` 两行截断；
  ③ `overflow-wrap:anywhere` 防长串不换行。副信息用单行 `text-overflow:ellipsis`。

## v8 严重 Bug 修复：云端记录主键字段用错（删除/修改从未回写）

### 现象
用户在页面删除一条健身记录，云端「健身记录表」里仍在。

### 根因（重要，全局性）
- 页内 SDK `db.query` 返回的记录对象是扁平的，**系统主键字段名是 `_id`**。
  依据：`page/database-sdk-contract.md` 第 201 行
  "A record is a flat object: `{ "fieldName": value }` (including the system primary key `_id`)"
- 而 `record_id` 是**服务端管理 API**（get_database_record / query_database_record 等脚本）返回的字段名。
- 页面 5 个 merge 函数（money / plan / fitness / shopping / media）全写的是 `r.record_id` → 永远 undefined
  → `remoteId: undefined` → `deleteRemoteXxx(rid){ if(rid) dbDelete(...) }` 直接跳过
  → **所有从云端加载出来的记录，删除和修改都只改了本地，云端纹丝不动。**
- 新建的记录不受影响（remoteId 来自 addRecord 返回值），所以这个 bug 一直没被发现。

### 修复（v8，7 删 7 增）
```js
id:(r._id||r.record_id||r.id||uid())          // 原 r.record_id||uid()       ×5
remoteId:(r._id||r.record_id||r.id||null)     // 原 r.record_id              ×5
cb(result.id || result._id || null);          // 原 cb(result.id || null)    ×1（addRecord 回写）
```
另把删除失败从 `goLocalOnly("删除失败")`（只 console.warn，用户完全无感）
改成 `console.warn(...)` + `toast("云端删除失败，请重试")`，以后同类问题能被看见。
用兼容链而不是直接替换成 `_id`，是为了两种 API 形态都能工作。

### 影响提示
- 用户之前"删掉"的那条健身数据仍在云端，v8 后刷新页面会**重新出现**，需要再删一次（这次会真删）。
- 同理，之前对云端数据做的任何编辑，也可能从未同步上去。

### 排查方法沉淀
读 `page/database-sdk-contract.md` 核对 SDK 返回结构，不要凭服务端脚本的返回字段名推断页内 SDK。

## v9 习惯打卡数据模型重构（用户提出疑问，评估后确认是缺陷）

### 用户疑问
点一次「喝水 +1」云端就多一行；点 −1 出现「0 杯」的行。
"我今天喝了 4 杯发现多记了一杯想减掉，结果记录里多出来好几条数据" —— 这符合预期吗？

### 评估结论：不符合，是数据模型缺陷（已修复）
1. **`pushHabit` 每次都 `dbAdd`**：没有更新路径，也不保存 rid。
   → 每点一次 +/- 就往 DB_HABIT 插一行新记录。云端实测：
   2026-10-05 喝水 7 行（1,2,1,0,0,8,0）、2026-10-07 喝水 8 行（1,0,1,2,3,2,1,0）、冥想 4 行。
2. **`mergeHabit` 是"后写覆盖"**：`remoteEntries[hname][d] = val`，多行时最后遍历到的赢。
3. **`dbFetchAll` 的 query 没传 `sorts`** → 返回顺序不保证 → **显示几杯可能每次刷新都不一样**。
   这比"多几条记录"更严重：读数不可信。

### 修复（v9）
- `mergeHabit`：记录每个 (习惯,日期) 的远端行 id 到 `h.remoteIds[date]`；
  `h.entries` 从"覆盖"改为"合并"（`Object.assign({}, h.entries||{}, remote)`），避免抹掉本地未同步的日期。
- 抽出 `habitProps(h,date,val)`；`pushHabit` 改 upsert：
  - 有 rid → `dbUpdate`
  - 无 rid → `dbAdd`，回调里记 id；期间若本地值又变了再补一次 update（防连点竞态）
  - 值 ≤0 → `dbDelete` 该行并清 rid（0 与"未打卡"等价，不留垃圾行）
- 连点保护：`h.pendingAdd[date]` 防止新增回调未回来时重复插入。
- `remoteIds` / `pendingAdd` 随 `JSON.stringify(state)` 持久化，刷新后可复用。

## v11 时间面板修复：点选时/分"没反应"（用户截图报告）

### 四个叠加根因（全都修了）
1. **外部点击关闭器误杀（主因）**：`dtPop` 点击处理器里 `dtBuild()` 用 innerHTML 重建列内容，
   被点的按钮在事件冒泡中途变成游离节点；事件到 document 的 closer 时
   `dtPop.contains(e.target)` 对游离节点=false → 误判"点了外面" → `dtClose()`。
   于是每次点击后面板立即关闭、`dtCur=null`，用户下一次点击落在已关闭的面板上
   （`dtSet` 因 `dtCur=null` 直接 return）→ "点击没反应"。只有"此刻"幸存是因为
   通常它是打开面板后的第一次点击（dtCur 还在）。
   → 修复：closer 加 `if(!e.target.isConnected) return;`
2. **data-h/data-m 从不写回**：点时/分只改内部变量 dtHour/dtMin，`完成` 也只关闭面板，
   从不调 dtSet → 值永远进不了 input（日期模式点天就 dtSet，所以日期一直正常）。
   → 修复：点时/分立即 `dtSet(时:分)`（面板保持打开，可连续调时和分）。
3. **dtOpen 顺序错误**：原顺序 `dtBuild() → dtPop.hidden=false`，列在 display:none 时构建，
   scrollTop 设置静默无效 → 打开面板永远停在顶部，选中值不在可视区
   （用户截图列从 02 开始、看不到选中的 10:09，即此因）。
   → 修复：先 `hidden=false` 再 `dtBuild()`；同时去掉 `.dt-col` 的 `scroll-behavior:smooth`
   （异步动画导致同步 scrollTop 读数不实测、且每次点选都从 0 重动画）。
4. **offsetParent 错误**：`.dt-col` 无 position → 按钮 offsetTop 以 dt-pop 为基准，多算头部高度。
   → 修复：`.dt-col{position:relative}`。

### 顺带
时间模式下隐藏顶部 ‹ › 月份按钮（在时间模式点了是空操作，同类"没反应"）；日期模式恢复显示。

## 时间选择器 v11→v12：循环滚轮（iPhone 闹钟式）

### v12 需求
用户确认 v11 已修好，但希望时间选择像 iPhone 闹钟一样**无限循环滚动**（23 后面是 00，59 后面是 00），
而不是 00-23 线性列表。已实现并发布（版本 12）。

### 实现（.workbuddy/tmp_wheel/ 下脚本）
- **5 份循环拷贝**：小时列 120 项、分钟列 300 项；`DT_ITEM=34`px、视口 170px、
  `midBase = floor(5/2)*n`（middle copy 起始项索引：小时 48、分钟 120）。
- **回绕守卫**（dtWheelSync）：居中索引 k 保持在 [n, 4n)，越界就整体跳 ±n*DT_ITEM
  （内容重复所以视觉无缝）；k%n 即真实值，滚动中实时 dtSet 写回（input+change 事件都派发，草稿保存依赖）。
- **纯 JS settle**（dtWheelSettle）：滚动停 140ms 后吸附到最近项。**放弃 CSS scroll-snap**：
  Chrome 在 innerHTML 重建后会 unpredictable 重吸附（设 1904 落到 340），值会写错。
- 点击某项 → dtCenterCol(smooth) 平滑居中；dtOpen 先 hidden=false 再 dtBuild（保证 clientHeight 可算）。

### v12 关键 bug（折腾最久的一个）
`dtCenterCol` 公式漏乘每份项数 n：`(mid + val)*ITEM` 把 copy 序号当项索引用 → 打开面板
滚到 copy0（开 10:09 实测居中在 12/11），点击项也被甩到错误 copy 再被守卫拉走。
正确：`(mid * n + val) * DT_ITEM - (clientHeight - DT_ITEM)/2`。
**交叉验证技巧**：测试脚本里手写 scrollTop 用的正确公式 (48+23)*34 反而全对——同一文件里
两套公式结果矛盾就是公式 bug 的信号。

点击居中/此刻/清除/日期回归/reopen 默认 9:00）+ 截图确认高亮带与渐隐。
